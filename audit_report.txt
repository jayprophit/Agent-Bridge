1. WORKSPACE ROOT VALIDATION
==================================================
STATUS: EXISTS_PARTIAL

Existing capability:
- RuntimeConfig.allowed_workspace_roots: list[str] validated at AgentRuntime.__init__()
- AgentRuntime.authorize_workspace(): resolves workspace path and checks it is relative to allowed roots, raises PermissionError if outside
- _root_rule(): validates root rules (allowed_modes, allowed_approval, quotas)
- Executor.resolve(): sandbox path protection - blocks absolute paths, traversal, escapes workspace
- Executor._is_protected_rel(): blocks .bridge internals modification

Gap analysis:
- WORKSPACE_INVALID: Partially covered - authorize_workspace raises PermissionError for outside roots
- WORKSPACE_OUTSIDE_ALLOWED_ROOT: Covered by authorize_workspace() PermissionError
- WORKSPACE_ROOT_MISMATCH: Not explicitly classified; root_rules validated but mismatch not reported as distinct error
- WORKSPACE_NOT_FOUND: Covered by sandbox (workspace not a dir raises ValueError)
- workspace='.' behavior: Falls through to Agent Bridge's own CWD (identified root cause of task failures)

NEW REQUIREMENT (not yet implemented):
- bad workspace configuration must fail BEFORE planner/model execution
- Currently: workspace config validated at session creation, but planner still starts; task gets stuck in PLANNING then fails

Error family proposed (not implemented):
- WORKSPACE_INVALID
- WORKSPACE_OUTSIDE_ALLOWED_ROOT
- WORKSPACE_ROOT_MISMATCH
- WORKSPACE_NOT_FOUND

Source files supporting existing capability:
- runtime.py: AgentRuntime.authorize_workspace(), _root_rule(), _validate_root_rules()
- config.py: BridgeConfig, RuntimeConfig, allowed_workspace_roots, root_rules, presets
- executor.py: Sandbox.resolve(), _is_protected_rel(), path traversal protection

11. FULL-STACK DEVELOPMENT PRINCIPLE
==================================================
STATUS: DOCUMENTED_NOT_IMPLEMENTED

Principle statement (from README/convention, not fully realized in tooling):
- Agent Bridge is NOT Python-centric
- Agent Bridge is NOT frontend-only
- Agent Bridge is NOT backend-only
- Must be capable of orchestrating: frontend, backend, databases, APIs, native applications, systems software, embedded/firmware, automation, data/ML, mixed-language systems
- Must use whatever compatible language/toolchain the project requires
- Must not promise a language is operational without its required local or connected toolchain

Reality check:
- Agent Bridge IS Python-weighted (ALLOWED_BINARIES_DEV/STRICT are Python-centric)
- Shell profile "dev" allows dotnet/node/npm; "strict" only Python
- C/C++ not supported (clang++ not in allowlist)
- Mixed-language projects not supported (see section 6)
- Toolchain neutrality not achieved

The principle is aspirational but the implementation is Python-biased.

Source files:
- README.md / convention: Full-stack development principle statement
- runtime.py: capabilities() lists modes ["build", "plan", "hybrid"], profiles
- README.md: "It is NOT Python-centric. It is NOT frontend-only. It is NOT backend-only."

15. VERSION RECOMMENDATION
==================================================

MAINTENANCE CANDIDATES (v0.8.2):

1. WORKSPACE/ROOT VALIDATION
   - Justification: Root cause of proven task failures (workspace='.' → Agent Bridge dir)
   - Code inspection: authorize_workspace() exists but "fail before planner" guard not enforced
   - Risk: LOW - config validation already present, just needs enforcement boundary

2. STRUCTURED WORKSPACE ERRORS
   - Justification: Clients need clear error, not opaque PLANNING→FAIL
   - Code inspection: PermissionError raised but not mapped to structured task.failed payload
   - Risk: LOW - error class exists, just needs payload mapping

3. BETTER FAILURE PROPAGATION
   - Justification: Task gets stuck in PLANNING then fails ~0.3s later; unclear why
   - Code inspection: planner.completed emitted but task.failed reason not propagated to API clients clearly
   - Risk: LOW - _execute() already captures exceptions, just needs API exposure

4. ROOT/SESSION INTROSPECTION
   - Justification: Clients cannot easily answer "what workspace is this task using?" or "what is the session state?"
   - Code inspection: authorize_workspace(), session.status, task_status() exist but not combined in single diagnostic
   - Risk: LOW - introspection endpoints exist (session_status, status_dashboard, diagnostics)

5. REGRESSION TESTS
   - Justification: No test coverage for workspace config failure mode
   - Code inspection: tests/ directory exists but workspace-config-failure not tested
   - Risk: LOW - add test scenarios

v0.8.2 MAINTENANCE RECOMMENDATIONS:
- Enforce workspace root validation before planner execution
- Map error classes to structured task.failed payload
- Expose session introspection via single diagnostic endpoint
- Add regression tests for workspace config failure modes
